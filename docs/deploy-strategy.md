# MaiBot 部署方案选型

## 先更正我上一版的两个错误

1. **容器镜像不占 GitHub Packages 的 500MB 额度**。那 500MB/1GB 只针对 npm、Maven、NuGet 等格式。GHCR 的容器镜像存储和带宽目前是**免费**的，GitHub 承诺变更前至少提前 30 天通知。
2. 你的方案不是「服务器构建」，准确说是 **Actions 编排 + 服务器构建**（CI 在 Actions，CD 在服务器）。

---

## 方案对比

| # | 方案 | 构建位置 | 优点 | 缺点 | 成本 | 适用场景 |
|---|---|---|---|---|---|---|
| A | 拉官方镜像 | 官方 CI | 最省事，1 分钟部署 | 跑不了你自己的代码 | 0 元 | 只用官方版，不改代码 |
| B | **Actions 编排 + 服务器构建**（你的） | 服务器 | 服务器只要 Docker；无外部依赖；代码即产物，不会脱节 | 构建吃服务器 CPU/内存；首次 15~20 分钟；回滚慢（要重建）；每次部署有停机 | 0 元现金，占用服务器资源 | 单机、自用、改动频繁 |
| C | Actions 构建 + 镜像仓库 | GitHub Actions | 部署快（只拉镜像）；服务器不构建；产物不可变；回滚改 tag 秒级；可多机 | 要维护 registry 可达性和凭证；多一层概念 | 见下表 | 多机、团队、要审计 |

**A 和 B 的本质区别**：B 的容器内代码 = 你仓库的代码；A 的容器内代码 = 官方仓库的代码，和你的 fork 无关。

---

## 方案 C 的三种仓库成本

| 仓库 | 存储费 | 出网流量 | 真实成本 | 主要限制 |
|---|---|---|---|---|
| GHCR | 容器镜像**目前免费**，公开包永久免费 | 免费 | **0 元** | 免费是「当前政策」不是承诺；国内服务器拉取可能超时 |
| Docker Hub | 私有 1 个免费，公开无限 | 免费 | **0 元** | 匿名拉取限 100 次/6 小时（单机部署不会触发） |
| 自建 registry（Harbor / registry:2） | 软件免费 | 走自己服务器带宽 | 磁盘 + 带宽 + 运维 | 磁盘要 ≥ 镜像体积 × 版本数；Harbor 最低 4GB 内存 |

结论：**成本不是方案 C 的障碍**，真正的障碍是「你的服务器能不能稳定访问 ghcr.io」和「愿不愿意多维护一层」。

## 怎么估计一个镜像的大小

三个方法，从粗到准：

1. **直接查现成的**（最快）：
   ```bash
   docker images sengokucola/maibot
   ```
   官方镜像最新版：**466 MB**（压缩后，即 `pull` 的下载量），展开占盘约 **1.3 GB**。

2. **推算自建镜像**：Dockerfile 相同 → 体积基本一致（±10%）。你的镜像不会比官方小，因为你没做额外瘦身。

3. **构建后精确读**：
   ```bash
   docker image inspect --format '{{.Size}}' maibot-local:latest
   ```

**仓库容量估算**（方案 C 用）：
- 镜像层是共享的，10 个版本不占 10 份体积
- 改代码只影响最后一层（`COPY . .`），每版增量约 **10~50 MB**
- 所以：`基础 466MB + 版本数 × 50MB`。10 个版本 ≈ 1GB

## 一句话选型

- 想「代码一推就生效、不想运维额外组件」→ **B**
- 想「部署快、能秒回滚、以后可能加机器」→ **C**
- 单机 + 国内服务器拉 ghcr 不稳定 → **B 更稳**，C 的收益抵不过网络风险
